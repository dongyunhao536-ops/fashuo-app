## 结论

这次体验变差的主因不是“Claude 写的规则 Codex 看不懂”，也没有证据证明由一次 Codex 系统升级单独导致。仓库内可以直接确认的原因是：迁移后的长入口继续叠加规则，同时又把全量个人快照、Skill Run 阶段、题面 Gate 和写回校验串成所有任务的统一前置流程。系统升级可能改变触发、上下文加载或 Hook 的表现，从而放大问题，但不能在没有宿主版本对照的情况下把它定为根因。

官方 Skills 模型采用渐进加载：先提供 `name/description`，触发后加载完整 `SKILL.md`，额外文件由 Skill 按需读取。因此入口越长、无条件必读越多，正常轮次的上下文与工具成本越高。参考：<https://developers.openai.com/plugins/concepts/skills>。

## 本轮实测

- 六个旧入口合计约 129,461 bytes；新入口合计 28,837 bytes，减少 77.7%。完整规则没有删除，移到各 Skill 的 `完整运行参考.md`。
- 旧 Run 遥测近两日的 `context_loaded`：p50 2.750 秒、p95/max 15.217 秒；此前逐入口实测约 2.8–7.6 秒。它还未包含材料检索、作答与输出时间。
- 新直接路径只初始化本地 Run 的微基准约 1.6–9.1 ms。这个数字只说明状态机本身很轻，不代表完整答题只需数毫秒；实际收益是跳过与已知目标无关的全量个人快照。
- 全仓回归：69 个测试文件、501 项测试通过；六个 Skill 均通过官方 `quick_validate.py`。

## 新架构

### 1. 入口只负责四件事

每个 `SKILL.md` 只保留：触发与负边界、路径选择、当前任务的硬门槛、输出底线。目标控制在 7 KB 内，不再把全部历史经验、日期、模板和例外塞进入口。

### 2. 三种运行路径

| 路径 | 适用场景 | 是否加载全量个人上下文 |
|---|---|---|
| 直接执行 | 用户已给题目、错题、T#、章节、篇目或答案 | 否 |
| 个性化选择 | 系统替用户选下一题、排今天任务、判断进度或跨科排序 | 是，只运行一次相关快照 |
| 事务写回 | 真实结果、台账、同步与销账 | 不以快照为前提，只认目标证据与业务回执 |

`context_loaded` 因此只保留在 `plan` 等个性化选择阶段，不再充当所有路径的通用许可证。

### 3. 长规则按场景读取

原入口内容移入各目录的 `完整运行参考.md`。这些文件没有 Skill frontmatter，且明确从属于新入口；只在目标分、里程碑、复杂生命周期、轮次扩展、特殊评分或少见写回场景读取对应小节。

### 4. 模型与脚本重新分工

- 模型负责：理解用户意图、拆争点、教学判断、涵摄、反馈和表达。
- 脚本负责：确定性材料检索、题面防泄题、答案键判分、台账结构核验、数据库写回与幂等同步。
- 正常命令成功后信任结构化回执；不为“证明脚本没问题”反复读取实现、扫描全库或重复查询同一材料。

## 不得为提速删除的门槛

- 法硕结论仍须本地材料检索，并按用户指定标准 → 《考试分析》→讲义→法硕真题裁判。
- 自拟检验题仍须通过题面完整性 Gate，防止泄答案或把原错答案写进题面。
- 英语阅读仍由同版试卷与答案键实算，主观题仍由参考答案和采分表评分。
- `result_recorded/writeback_verified` 仍只能由真实业务命令签发；模型不能口头补签。
- 事件销账、主题稳定、背诵冷检和能力画像仍使用各自的数据门槛。

## 后续验收

测试通过只能证明契约一致，不能替代真实使用体验。接下来用 10–20 个真实学习轮次观察：

1. 已知目标的直接路径不应出现 `context_loaded`。
2. 一轮最多一次相关快照，同一批独立争点合并为一次材料加载。
3. 不再因缺少无关个人快照而 BLOCK；缺材料、题面、答案键、台账或写回仍必须 BLOCK。
4. 入口持续小于 7 KB；新增长期规则优先进入对应参考文件或确定性脚本。
5. 监控应分别统计直接路径与规划路径，旧 p95 样本过窗后再判断真实提速幅度。

## 维护原则

以后出现一次事故时，先修最小事实源或业务校验，不把新的“每次必做”直接追加到六个入口。只有跨 Skill、每轮都必要且可被测试的规则才进入共享契约；其余规则按场景放入参考文件，并配一条针对真实事故的回归测试。

## 第二阶段：规则代码化

<!-- [gpt] 2026-08-13：停止继续压缩入口，开始把重复确定性约束下沉为机器 Gate。 -->

入口从 129 KB 降到 28 KB 后，不再把压缩 `SKILL.md` 当主目标。下一阶段按“判断留给模型、约束交给代码”推进：模型负责识别真实错误、稳定主题和错因；脚本负责字段存在性、枚举、状态一致性、来源、章节、幂等与写回顺序。

第一条纵向切片是 `validateErrorEntry()`：

- 单条 `add` 暂存前校验；`--chapter` 可独立于主题保存，非复发新错不得漏章节。
- `record-batch` 生成每道 `new_error` 时复用同一函数，批次章节自动传入，不再维护第二套 topic 规范化代码。
- 最终 `syncStudyOutbox()` 先校验整份 outbox，再做任何远端调用；手改缓存不能绕过，后段坏条目也不会导致前段先写入。
- 来源是受控 `direct / batch / recurrence`，由入口赋值；数据库继续使用兼容的 `pc复盘 / pc复盘·复发` 展示值。
- 主题或病根未知时明确落 `pending / unclassified`，不把“机器强校验”误做成“逼模型猜 confirmed”；一旦声称病根 confirmed，就必须有具体代码和用户认领/证据说明。
- 校验失败返回总码 `ERROR_ENTRY_INVALID` 与字段级错误码，调用方可直接修对应字段，不再让模型回读长篇规则定位失败原因。
- 校验器上线前已经留在本地的旧 outbox 只在最终边界显式迁移并标“历史待补章节”；新写入不享受兼容放宽。

后续应按实际事故频率逐条迁移，不一次性重写全部 Skill。优先候选是主观题评分写回、复检证据和带背台账；每次都要求“一个统一函数 + 所有写入口 + 最终边界 + 绕过测试”，否则只是把文字规则换了存放位置。
